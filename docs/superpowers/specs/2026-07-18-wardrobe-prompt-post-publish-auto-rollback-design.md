# 衣橱 Prompt 发布后自动回滚设计

## 目标

移除普通顾问端的 `Prompt优化` 入口，让 Prompt 的生命周期完全由后端自动管理。自动发布的新 Prompt 积累足够数量的顾问评测数据后，系统使用相同图片将它与上一个已退役版本进行比较；只有确认新版本明显退步时，才自动恢复上一个版本。

数据库继续保留 Prompt 版本、优化任务、实验结果和只追加的审计历史。移除前端入口不等于删除这些后端控制能力和历史记录。

## 已确认的设计决定

- 候选 Prompt 生成、发布前评测、发布和发布后回滚都由后端判断。
- 顾问端评测管理首页不再显示 `Prompt优化` 按钮。
- 不能把不同批次数据的原始反例比例作为回滚依据。
- 回滚判断必须让两个 Prompt 使用相同的已评测图片和相同的顾问最终答案。
- 历史衣物数据和 AI 原始快照保持不可修改。
- 后端继续保留经过身份认证的紧急回滚接口，但普通顾问页面不提供入口。

## 备选方案

### 方案一：直接比较原始反例比例

这个方案改动最小，但不采用。不同 Prompt 版本面对的衣物类别和识别难度可能不同，反例比例更高可能只是因为新一批图片更难，并不能证明 Prompt 更差。另外，正例和反例只是二元分类，也无法体现错误的严重程度。

### 方案二：发布后进行同图影子评测

采用这个方案。新发布 Prompt 的真实 AI 原始结果已经永久保存，可以直接与顾问最终答案比较。系统再让已退役的上一个 Prompt 对同一张图片进行一次影子识别，并与同一个顾问最终答案比较。最后使用配对后的完全匹配率和风格平均绝对误差判断是否需要回滚。

每个观察样本只额外增加一次 Gemini 调用，而且比较的是用户实际收到的新版本识别结果。

### 方案三：只保留人工回滚

这个方案运维简单，但不符合已经确认的全自动流程。人工回滚接口仅作为后端紧急手段保留。

## 范围

### 包含

- 删除评测管理首页的 `Prompt优化` 按钮及其跳转方法。
- 新增发布后监控表和逐条影子评测结果表。
- 每次自动发布成功后，自动创建唯一的发布监控任务。
- 累积由新发布 Prompt 识别并完成顾问评测的衣物。
- 达到门槛后冻结一批观察样本。
- 让上一个已退役 Prompt 对这些图片执行影子识别。
- 将两个版本的结果与同一个顾问最终答案进行比较。
- 自动决定保留新版本或者回滚到上一个版本。
- 将自动回滚写入只追加的 Prompt 版本审计表。
- 后端重启后恢复正在收集或正在评测的监控任务。
- 新版本发布后仍处于观察期时，不允许开始下一轮 Prompt 优化。

### 不包含

- Gemini 微调或模型权重训练。
- 重新识别或修改已有的衣橱业务数据。
- 使用未评测或 `ai_failed` 的衣物作为判断证据。
- 在不相关的历史版本之间自动切换。
- 在顾问端提供生成、发布或回滚按钮。

## 数据流程

1. 现有自动优化器发布候选版本 `V2`，将上一个版本 `V1` 标记为 `retired`，并写入一条 `auto_publish` 审计记录。该记录的 `sample_floor_item_id` 保存发布时衣物表的最大 ID。
2. 定时恢复任务根据这条审计记录创建唯一的发布监控任务。重复执行不会创建重复任务。
3. 监控任务进入 `collecting` 状态，只收集 `prompt_version_id` 为 `V2`、已经完成顾问评测、字段格式正确，并且 ID 大于发布水位的衣物。
4. 收集数量达到配置门槛后，系统冻结这些衣物 ID，监控任务进入 `evaluating` 状态。
5. 对每个冻结样本，将已经保存的 `V2` AI 结果与顾问最终答案比较；同时让 Gemini 使用 `V1` 对同一张图片进行影子识别，再与同一个顾问答案比较。
6. 每条评测结果先持久化，再进行汇总判断。后端重启后可以继续处理尚未完成的记录，不会创建第二个监控任务。
7. 如果上一个版本根据自动回滚策略被证明明显更好，后端在一个事务中重新激活 `V1`、退役 `V2`、写入 `auto_rollback` 审计记录、将不兼容的优化任务标记为 `stale`，并推进样本水位。
8. 如果没有明确退步，监控任务变成 `kept`，继续使用 `V2`，之后的自动优化可以使用更新的顾问评测样本。

## 样本资格和快照规则

一个观察样本必须同时满足：

- `qj_wardrobe_item.status = 'completed'`。
- `prompt_version_id` 等于监控任务对应的新发布版本。
- `ai_evaluation_json` 和 `advisor_evaluation_json` 都存在，并通过现有 `WardrobeEvaluationNormalizer` 数据格式校验。
- 衣物不是 `ai_failed` 状态。
- 衣物 ID 大于自动发布审计记录中的样本水位。
- 同一个衣物没有被重复加入同一个监控任务。

监控任务进入 `evaluating` 后，已选择的衣物 ID 不允许再改变。

## 数据持久化设计

### `qj_wardrobe_prompt_release_monitor`

- `id`：主键。
- `publication_audit_id`：对应 `auto_publish` 审计记录，具有唯一约束。
- `optimization_id`：发布该 Prompt 的自动优化任务 ID。
- `published_prompt_version_id`：当前观察的新发布版本。
- `baseline_prompt_version_id`：刚刚退役的上一个版本。
- `status`：`collecting`、`evaluating`、`kept`、`rolled_back`、`failed` 或 `stale`。
- `sample_ids_json`：开始评测后不可修改的衣物 ID 快照。
- `threshold_json`：本次任务冻结的最少样本数、失败率和退步门槛。
- `published_metrics_json`：新发布版本的汇总指标。
- `baseline_metrics_json`：上一个版本的汇总指标。
- `decision_reason`：机器可读的最终决定原因。
- `sample_max_item_id`：本次观察中最大的衣物 ID，自动回滚时作为新的样本水位。
- 创建时间、评测开始时间和结束时间。

`publication_audit_id` 的唯一约束保证定时恢复任务不会重复创建监控记录。

### `qj_wardrobe_prompt_release_result`

- 每个 `(monitor_id, wardrobe_item_id)` 组合只有一条记录。
- 状态为 `pending`、`running`、`completed` 或 `failed`。
- 保存新发布版本的不可变 AI 结果、上一个版本的影子识别结果、两份差异数据、重试次数、错误信息和时间。

该结果表与衣橱业务表隔离，不修改衣物数据。

### 审计表扩展

为 `qj_wardrobe_prompt_version_audit.action` 增加 `auto_rollback`。执行者记录为 `system:auto-monitor`，原因记录配对评测的退步结论，`sample_floor_item_id` 保存监控样本中的最大衣物 ID。

新的 `auto_publish` 审计记录也必须在发布事务中写入当时的 `sample_floor_item_id`。如果旧的自动发布记录没有该水位，监控恢复时使用对应优化任务的 `sample_max_item_id` 作为后备值。

## 自动回滚规则

默认配置采用保守策略，并允许通过配置文件调整：

- 测试环境观察数量：4条已评测衣物。
- 正式环境观察数量：20条已评测衣物。
- 影子识别最大失败率：20%。
- 完全匹配率最小退步幅度：正式环境 0.10，测试环境 0.25。
- 风格平均绝对误差最小退步幅度：5.0个百分点。
- 影子识别重试次数：2次。

只有同时满足以下条件，才允许自动恢复上一个版本：

1. 监控任务观察的版本仍然是当前生效版本，其对照版本仍然是直接上一个版本。
2. 成功的配对评测数量达到门槛，而且所有冻结记录都已经进入终态。
3. 影子识别失败率没有超过配置上限。
4. 上一个版本在两个指标上都不比新版本差：
   - 上一个版本的风格平均绝对误差小于或等于新版本；
   - 上一个版本的完全匹配率大于或等于新版本。
5. 至少达到一项明确退步门槛：
   - 上一个版本的完全匹配率比新版本高出配置的最小幅度；或者
   - 新版本的风格平均绝对误差比上一个版本至少高出配置的最小幅度。

如果证据不足、两个指标互有胜负或者结果矛盾，系统保留当前新版本。系统绝不会仅仅因为原始反例比例升高就自动回滚。

## 状态和并发规则

- 当前生效版本最多只能有一个未结束的发布监控任务。
- 已经开始的发布前优化任务可以正常完成，但是新版本存在 `collecting` 或 `evaluating` 监控任务时，不允许开始下一轮自动优化。
- 如果当前 Prompt 因为其他原因发生变化，监控任务变成 `stale`，不能再切换版本。
- 自动回滚时，对当前版本、目标版本、监控任务、优化任务和审计写入使用数据库行锁。
- 重复事件、定时恢复和进程重启必须保持幂等，不能产生重复任务或重复版本切换。

## 失败处理

- Gemini 影子识别发生临时错误时，最多重试配置的次数。
- 单条记录最终失败后，计入失败率保护条件。
- 失败率过高时，监控任务变成 `failed`，不能自动回滚。
- 数据库冲突或版本状态冲突会让监控任务变成 `stale` 或 `failed`，但不会改变当前生效 Prompt。
- 唤醒事件失败后，由每60秒运行一次的定时恢复任务继续处理。
- 发布后监控失败不能影响顾问已经成功提交的衣物评测。

## 前端调整

删除评测管理首页的 `Prompt优化` 按钮和 `toPrompt()` 方法。Prompt管理页面和后端查询接口可以保留用于开发调试，但普通顾问没有页面入口，也不在日常流程中执行任何 Prompt 生命周期操作。

## 测试要求

后端测试必须覆盖：

- 每条自动发布记录只能创建一个监控任务。
- 只能选择由新发布 Prompt 识别、已经完成顾问评测且数据格式正确的衣物。
- 冻结样本后，后续新增评测不能改变本次样本快照。
- 新发布版本和上一个版本必须与同一个顾问最终答案比较。
- 仅仅出现原始反例率差异不能触发回滚。
- 完全匹配率明确退步时触发自动回滚。
- 风格平均绝对误差明确退步时触发自动回滚。
- 指标互有胜负、样本不足或失败率过高时保留当前版本。
- 当前生效版本变化后，监控任务变成 `stale`。
- 自动回滚必须在事务中完成、写入审计、推进样本水位，并将不兼容任务标记为 `stale`。
- 后端重启后能继续处理已持久化的评测记录且不重复执行。
- 发布后监控结束前不能开始下一轮自动优化。

小程序测试必须验证评测管理首页不再包含 Prompt 跳转按钮和跳转方法。

## 部署要求

- 新增一份可重复执行、兼容 MySQL 5.7 的迁移脚本，用于创建两个监控表并为审计动作增加 `auto_rollback`。
- 启动新版后端前，先在测试数据库执行迁移脚本。
- 测试环境和正式环境的门槛继续放在各自的配置文件中。
- 现有 Prompt 版本、审计记录、优化任务和衣橱历史数据不需要重写。
